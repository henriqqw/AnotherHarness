# 工程原则

[English](engineering-principles.md) | 中文

本参考文档列出每个 AnotherHarness 变更都遵循的设计原则。[架构](architecture.zh.md)定义这些原则所保护的结构，[defensive-patterns.zh.md](defensive-patterns.zh.md) 涵盖故障处理。现有代码违反某项原则时，应在覆盖该领域的[规格](spec-driven-development.zh.md)中改进；无关的工作不夹带顺手重构。

## 插件架构中的 SOLID

- **单一职责。** 一个包负责一项能力，一个模块只有一个变更理由。混合了策略与机制、I/O 与纯逻辑、或两个独立变化关注点的模块应拆分。
- **开闭原则。** 通过文档化的扩展点扩展行为：Cordis 服务、类型化事件、waterfall 与注册表。不要为了增加行为而修改 agent 循环或根据调用方身份分支。
- **里氏替换。** [能力接缝](capability-seams.zh.md)的每个提供者都遵守完整的服务契约，包括失败语义与取消。契约测试针对每个提供者运行。
- **接口隔离。** 服务定义只暴露其消费者所需的最小接口。优先使用多个聚焦的服务，而不是一个宽泛的服务。
- **依赖倒置。** 消费者依赖服务定义，从不依赖具体提供者，例如 `*-local`、`*-ssh` 或 `*-sandbox` 包。由 profile 与 bundle 选择提供者。

## 分层

依赖指向内层：应用依赖 bundle，bundle 依赖提供者，提供者依赖服务定义，服务定义依赖核心包，所有层都可以依赖 `util`。低层从不导入高层，`util` 包不依赖任何工作区包。[模块图](module-graph.zh.md)展示当前的依赖边。

## 整洁代码

- 名称揭示意图；读者仅凭函数名与签名即可理解函数。
- 一个函数在单一抽象层级上只做一件事。
- 没有死代码、被注释掉的代码或推测性的选项。
- 边界携带显式类型；不透明标识符使用品牌类型（branded）。
- 失败是带有可操作信息的类型化值，参见 [defensive-patterns.zh.md](defensive-patterns.zh.md)。
- 随部署变化的值是经过校验的配置字段；协议常量具名。

## 测试即规格

测试描述可观察行为，而不是实现步骤。优先使用聚焦的单元测试，并为每个接缝提供一个契约测试。不要 mock 被测代码。每条规格验收标准至少对应一个具名测试。

## 可扩展性

新能力以接缝背后的新包形式加入，因此可以在不修改无关包的情况下新增、替换或移除。启动成本与每轮工作量与 profile 加载的插件数量成正比。
