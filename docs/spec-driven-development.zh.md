# 规格驱动开发（Spec-Driven Development）

[English](spec-driven-development.md) | 中文

本参考文档定义 AnotherHarness 的变更如何被规格化、批准、实现与验证。每个非平凡变更都从一份书面规格（spec）开始；代码实现规格，测试证明规格。平凡变更（如错别字修正、依赖升级、带有显而易见回归测试的单行修复）可以跳过规格，但仍须附带测试。

## 工作流

1. **规格化。** 将 [`specs/_template.md`](../specs/_template.md) 复制为 `specs/<area>/<NNNN>-<slug>.md`，其中 `<area>` 是所属的包分组，`<NNNN>` 是该分组中下一个可用编号。填写问题、目标、非目标、用户可见行为、验收标准、契约、风险与发布方式。将状态设为 `draft`。
2. **评审。** 用户在实现开始前批准规格，状态变为 `approved`。未解决的问题会阻止批准；作者应提出问题，而不是猜测答案。
3. **计划。** 在规格中加入实现计划：受影响的包、新增或变更的[能力接缝（capability seam）](capability-seams.zh.md)、迁移步骤，以及与每条验收标准对应的测试清单。
4. **实现。** 以小而可评审的步骤推进。每条验收标准至少对应一个自动化测试，测试名称包含该标准的 ID（`AC-1`、`AC-2`……）。偏离规格时先更新规格。
5. **验证。** 运行 [development.zh.md](development.zh.md) 中的聚焦检查，然后在规格的验证表中记录证明每条标准的测试。将状态设为 `implemented`。
6. **文档。** 按照 [docs/AGENTS.md](AGENTS.md) 更新所属文档层级；对外部可感知的破坏性变更，同时更新升级指南。

## 规格规则

- 规格描述行为与契约，而不是代码已经表达的实现细节。
- 一份规格只覆盖一项用户可见能力；需要超过约 300 行的规格应拆分。
- 验收标准采用“给定上下文，当执行动作，则出现可观察结果”的形式，且可以独立测试。
- 契约一节列出每个服务定义、事件、配置字段与 Session 日志变更。按照[架构](architecture.zh.md#session-log)，任何对模型可见的输入都需要一个 Session 事件。
- 拉取请求（PR）描述中链接其规格。
- 规格在实现后保留在仓库中，作为该行为存在原因的记录；后续替代它的规格将旧规格状态设为 `superseded` 并链接继任者。

## 与 Agent Notes 的关系

规格负责需求及其验收标准。[Agent Note](../.agents/notes/README.zh.md) 负责设计决策及其理由。规格链接其依赖的笔记，笔记链接促成它的规格。
